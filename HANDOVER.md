## 2. How we work (please keep doing this)
1. The assistant builds changes in a clone of the repo, runs `npm test`, the build and `npm audit`, and delivers a **zip of only the changed files** plus a short summary.
2. The developer unzips over the project (overwriting), runs `npm test`, deploys (`firebase deploy --only ...`), tests on a phone, then commits and pushes.
3. The assistant then **verifies the pushed commit on a fresh `git clone`**: files identical to what was sent, clean `npm ci`, build, tests, audit, no secrets tracked.
4. Style: concise English, plain words, commands for **PowerShell**, at most one question per reply, state assumptions instead of asking when a sensible default exists. Mention anything not verified live (rules, email, schedulers).
5. Earlier mix-ups came from a zip saved in the wrong place. When something "doesn't change", check the file on disk (`Select-String -Path ... -Pattern ...`) before debugging.

**Saving tokens in a new session:** do not print or rewrite whole files. Use `git clone`, `grep`, and small targeted edits (Python `str.replace` with an assert that the old text exists). Re-use the test helpers already in `tests/`. Do not repeat the README back.

## 3. Stack
- Frontend: React 18, Vite 8, React Router 7, Firebase web SDK 13, plain CSS in `src/styles.css`. No UI library.
- Functions: Node 22, `firebase-admin` 14 (**modular API only**: `getAuth()`, `getFirestore()`; `admin.auth()` no longer exists), `firebase-functions` 7 (v2 style).
- Tests: Vitest 5 + jsdom + Testing Library (`npm test`), and `node --test` for functions (`cd functions && npm test`). Currently 218 app tests (19 files) and 76 function tests, all passing. The app's `npm audit` is clean. `functions` shows 6 moderate advisories (glob, minimatch, rimraf, gaxios, gcp-metadata, google-gax) deep inside Google's own Firestore library: `npm audit fix` cannot resolve them (it needs major-version jumps in Google's packages), our code cannot reach them, so wait for a newer `firebase-admin`/Firestore release and re-check now and then; do not use `--force` or add overrides. (The root `package.json` has an `overrides` entry that pins `@grpc/grpc-js`.)
- Env: `.env.local` holds `VITE_FIREBASE_*` and optional `VITE_MAPS_EMBED_KEY`. Anything `VITE_` is public. Real secrets only ever go in Functions.

## 6. Decisions already made
- Clubs and events start **pending** and need an admin/superadmin to approve; admin-created items are auto-approved; owner edits to approved items keep them live. Legacy clubs without a status are approved from the Approvals tab.
- "Other" exists for discipline, species, waterbody, scoring method, division and reasons. **Not** for fishing type, status, format, role, region. Club membership uses "Independent".
- Organiser role requests: `roleRequests/{uid}` (one per person), asked from My page (`organiserRequests.jsx`), decided in Admin → Approvals → Organisers; both go through functions (`functions/organiser.js`), the role is given with custom claims, and the new role reaches the person through `useAuth().refresh()`. The count joins the red pending numbers (`pendingCount(clubs, events, requests)`). Deleting a user also deletes their request; promoting someone on the Users tab settles it.
- Pending-approval numbers are one style everywhere: a small red superscript (`.bdg` inside a `.nl` wrapper around the label, component `PendingBadge` in `approvals.jsx`), as on the main menu's Admin link. Hidden when zero; screen readers still hear "N pending". Grey `.bdg.zero` is used for plain counts.
- Deleting is permanent and cascades (see README, "Deleting data"). It only happens through the delete functions, behind a dry-run preview and a typed DELETE (case-insensitive, surrounding spaces ignored). Do not add `deleteDoc` calls in the browser for clubs or events: the rules refuse admins, and a raw delete would orphan registrations, evidence and pictures. A user who owns events or clubs is deleted only together with them.
- Public participant list = names (plus team and club). Phone and email are private (organiser, admins, the person).
- Registration: account required; closes when the event starts, or when it ends if the organiser chooses; cancelling allowed until the start; the browser never writes registrations (functions only).
- Emails go to the `mail` collection and are sent by our own function `sendQueuedMail` (`functions/mailer.js`, nodemailer) through **Brevo** SMTP (free plan, domain authenticated by DNS). From `events@fishingleague.co.nz` (no mailbox), replies via `MAIL_REPLY_TO` (a Gmail chosen by the client). The SMTP key is the Functions secret `SMTP_PASSWORD`. **Do not use the Firebase Trigger Email extension or any Firebase Extension: the service is being shut down on 31 March 2027** (installed ones keep running but can no longer be changed). Details in the README ("Custom domain, DNS and email").
- Google sign-in uses Google Identity Services plus `signInWithCredential` (`src/googleSignIn.js`), with Firebase's popup only as a fallback. Reasons found on real phones: an installed copy of the app captures `/__/auth/handler` (white page), `signInWithRedirect` gives "missing initial state", and on a site Chrome has flagged for ads its ad filter blocks Firebase's `/__/auth/iframe` (console: "Chrome blocked resource … tends to show ads"). Clearing that flag is a separate job in Google Search Console (Ad Experience / Abusive Experience reports). The registrar's leftover `mail` CNAME serves their placeholder page and can be removed. Details in the README.
- Domain and sign-in: DNS is only changed through the registrar's chatbot, and web hosting must never be bought there. The sign-in handler uses the custom domain (`VITE_FIREBASE_AUTH_DOMAIN=fishingleague.co.nz` in the git-ignored `.env.local`, plus the OAuth redirect URIs and Authorized domains listed in the README). `.env.local` also holds the storage bucket `fishing-league-93bd0.firebasestorage.app`.
- Facebook and Microsoft sign-in were discussed and **deferred**.
- Times are always on a New Zealand clock. Photos: covers 16:9 up to 1280x720, avatars square up to 512x512, full photos up to 4 MP, all JPEG, Storage rules cap uploads at 2 MB as a safety net.

## 7. Traps already hit (do not repeat)
- **Never define a component inside another component.** It remounts on every render and inputs lose focus after each keystroke. Use module-level helpers like `Field`.
- Adding a field to clubs or events means touching **five places**: the form's `blank`/`from...`/`to...Data`, `validate...`, the rules' `hasOnly` list and validation, the README data model, and tests. A script that compares written keys to the rules' allow-list caught a missing field once.
- Firestore rules cannot hide single fields, hence the separate private registration record. Rules `get()` costs a read.
- The assistant's container shell is `sh`, not bash: no brace expansion or `<( )`.
- Appending to a file without a trailing newline glued a comment onto `.env.example` once.
- Custom-claim role changes reach a person's token within an hour (or at next sign-in).
- First deploy of a Firestore trigger can fail with an Eventarc permission message; wait a few minutes and redeploy.
- Google sign-in is blocked inside Messenger/Facebook in-app browsers: the sign-in sheet explains this (it now also hints for Telegram, Viber, VK, OK, TikTok, Line and other web views).
- **Installed copy of the app (the site has a web manifest):** on Android it captures in-scope addresses such as `/__/auth/handler`, so Firebase's popup sign-in ends in a white page. `signInWithRedirect` fails with "missing initial state", and `authDomain=fishing-league-93bd0.firebaseapp.com` fails the same way. Keep `authDomain=fishingleague.co.nz` and the Google Identity Services sign-in.
- **Windows deploys can time out** with "Cannot determine backend specification. Timeout after 10000": the code is fine, the machine is slow. Set `$env:FUNCTIONS_DISCOVERY_TIMEOUT="60"` in the same PowerShell window and deploy again.
- A saved `SITE_URL` in `functions/.env*` overrides the default in `index.js` (emails once showed the old address with `//me`). Links are now built with trailing slashes stripped.
- `firebase ext:install` only saved a setup into `firebase.json` and `extensions/` (which got committed). Both were removed; never bring them back, because a plain `firebase deploy` would install the extension and every email would go out twice.
- Tests must not depend on the clock or the machine's speed: use fixed timestamps (a list-order test failed only on the slower machine).
- `npm audit fix` with a different npm version can rewrite the whole root `package-lock.json` (a 3000-line diff). Patch just the one vulnerable entry in the lock instead, then `npm ci` and audit to verify.
- Brevo: the SMTP login is `…@smtp-brevo.com` (not the account email); never switch on "block unauthorized IP addresses for SMTP keys" (Cloud Functions have no fixed IP, so sending would fail); if the SMTP key was shared by email or chat, create a new one and run `firebase functions:secrets:set SMTP_PASSWORD`, then redeploy functions.
- The reply-to Gmail lives in the git-ignored `functions/.env.fishing-league-93bd0` (`MAIL_REPLY_TO=...`): keep a copy of that file.
- The assistant's container: wrap long shell commands in `timeout` (one that never returned ended the session), and use `bash` scripts for anything with `<( )`.

## 9. Open investigations (sign-in on phones)
1. **Installed app captures the sign-in window.** Confirmed by the developer: with the installed app and Android's "Open supported links" on, Chrome's Google sign-in popup reaches Google, lets you choose the account and then ends in a white page; turning that setting off makes it work. Implemented fix: Google Identity Services (`src/googleSignIn.js`). Waiting for phone tests (section 8). If it still fails, next idea: sign in with a redirect only when the app runs as an installed app (`display-mode: standalone`), and check a separate sign-in subdomain such as `auth.fishingleague.co.nz`.
2. **A second user cannot sign in on a phone (Chrome, no app installed).** His DevTools console showed Chrome's ad filter: "Chrome is blocking ads on this site because this site tends to show ads that interrupt, distract, mislead…" and "Chrome blocked resource https://fishingleague.co.nz/__/auth/iframe?…" (Firebase's sign-in helper frame, which looks like an ad frame to the filter). Our site shows no ads, so the domain is probably flagged because of its history (the registrar's default parking page or a previous owner). The new Google sign-in does not use that frame, which may remove the symptom. Still to do: (a) ask the user to retest after the new deploy; (b) in Google Search Console add `fishingleague.co.nz` as a Domain property (DNS TXT through the registrar's chatbot), then open the Ad Experience and Abusive Experience reports (Web Tools, under Legacy Tools), fix what they list and request a review; (c) `http://mail.fishingleague.co.nz` shows the registrar's "starting page": ask the chatbot to delete only the `mail` CNAME (keep the MX and `mx` records, because a domain without a mail server can look suspicious to spam filters); (d) quick workaround for an affected Chrome user: Site settings → Ads → allow for the site, or use another browser. Note: his phone also logged `ERR_CONNECTION_ABORTED` for Firestore, probably a side effect.
